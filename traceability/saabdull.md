**Target feature:** Multi-Repo: one session works across several repository roots, and each extra root is reached through an alias (its folder name). Main source files:

- [`packages/core/src/project/roots.ts`](../packages/core/src/project/roots.ts): root list, aliases, path display and resolution
- [`packages/opencode/src/project/instance-context.ts`](../packages/opencode/src/project/instance-context.ts): `containsPath`, `resolvePath`, `displayPath` used by the tools

- [`packages/tui/src/feature-plugins/sidebar/repos.tsx`](../packages/tui/src/feature-plugins/sidebar/repos.tsx): Repositories sidebar (add / remove)

All properties are in [`packages/opencode/test/project/multi-repo.property.test.ts`](../packages/opencode/test/project/multi-repo.property.test.ts) (abbreviated "property file" below). Run with `bun test test/project/multi-repo.property.test.ts` from `packages/opencode`.

| R2 (Step 1) | Removing a repo should remove it from the active repo list without affecting other repositories. | Removing a repo removes only that repo from the active list. Every other repo stays listed and is still reached by the same absolute path and the same alias, and files already written to disk are untouched. | Checkability: "without affecting" did not say what must stay the same (list membership, order, the alias the agent uses, or files on disk), and the acceptance criteria only checked membership. | R2 (Step 3) | The Step 1 wording above. | Removing a repo removes only that repo from the active list. ## Triage

First run against `main` (commit `cc92629c`): 4 passed, 3 failed. Every failure and how it was resolved:

| Property | Shrunk counterexample | What it showed | Outcome | Fix |
|---|---|---|---|---|
| R2 invariant | Roots `/x/web`, `/z/web`; remove `/x/web` | Same-name repos were numbered by position (`web`, `web-2`), so removing one renumbered the others. With three `api` repos, `api/f.ts` silently moved to a different repo. | Code bug | `b595f604`: same-name repos get `name-<hash of path>` aliases, which never depend on order. |
| R2 invariant | Same as above, after the fix | The repo that stopped sharing a name went back to its plain name, so the property's "alias string is identical" check still failed, although R2 only requires the repo to be *reached* by its old alias. | Code bug and wrong test | `b595f604`: `resolve` keeps accepting a repo's hashed alias. `ee98db13`: the property checks that the old alias still reaches the same repo. |
| R2 invariant | Roots `/x/api`; remove `/x/api` | Back to a single repo, the primary's old alias `main/f.ts` resolved to `/w/main/main/f.ts`, because single-repo sessions do not use aliases. | Requirement problem (conflict) | R2 revised (Requirement changes, R2 Step 3). `ee98db13`: the property checks single-repo behavior once one repo is left. |
| R3 round-trip | Primary `/x/api`, root `/x/src`, file `/x/api/a\b.txt/index.ts` | `resolve` split paths on `\` as well as `/`, so a file whose name contains a backslash (legal on Linux) came back as a different path. | Code bug | `b595f604`: split on the platform separator only. |

Passed on the first run: R2 round-trip, R3 invariant, R4, R6. After the fixes all seven properties pass, along with the existing `packages/core/test/project-roots.test.ts` (two tests that expected positional suffixes such as `repo-a-2` were updated to expect stable, distinct aliases) and `packages/opencode/test/server/httpapi-multi-repo.test.ts`.

Known limitation, not covered by R2 to R6: when an added repo's alias matches a folder in the primary repo (for example a repo named `src`), a relative path like `src/index.ts` goes to that repo, not to the primary's `src/` folder. Fixing it needs filesystem checks in the tools, so it is left for a later project.
