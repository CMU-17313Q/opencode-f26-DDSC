## Requirement changes

| ID | Original requirement (P4A) | Revised requirement | Why it changed |
|---|---|---|---|
| R1 | When a command matches several rules, the last matching rule in the config decides the outcome. | Withdrawn | Not a real requirement: it is the workbook's example row, left in by mistake. It is about permission rules rather than Multi-Repo, and its evidence (C-12) does not exist in my interview notes. |
| R2 | Removing a repo should remove it from the active repo list without affecting other repositories. | Removing a repo removes only that repo from the active list. Every other repo stays listed and is still reached by the same absolute path and the same alias, and files already written to disk are untouched. | Checkability: "without affecting" did not say what must stay the same (list membership, order, the alias the agent uses, or files on disk), and the acceptance criteria only checked membership. The revision spells out the parts the interviewees named: the list returns to its previous state (C-4, S-4), files on disk stay (C-5, O-4), and the agent must not end up in the wrong repo (O-2, C-7), which means surviving repos keep their alias. |
| R3 | Repos with identical names must be distinguished. | Repos with the same folder name get distinct aliases, and every displayed file path resolves back to that exact file. | Checkability: "distinguished" did not say where (sidebar, displayed paths, or path resolution). The original acceptance criteria used an absolute path, which is resolved without looking at repo names at all, so they could pass even if two `api` repos were indistinguishable. The revision checks the names the agent actually uses, as S-6 asked: identity comes from paths, not display names. |
| R5 | Acceptance criteria: Add A then B and resolve an absolute path in B. Repeat with B then A. Both operations resolve to the same file in B. | Same requirement. Acceptance criteria now also cover a path qualified with B's alias. | Checkability: the requirement says "explicitly qualified file paths", which includes alias-qualified paths such as `api/src/x.ts` (the form the agent is told to use), but the criteria only tested absolute paths, which never depend on order. |
| R6 | None (not in the P4A table) | A path outside every active repo is never treated as inside the project: a tool must ask for `external_directory` permission before touching it. | Added in P4B: it is the theme all three interviewees raised (C-3, S-2, S-3, O-3) but it was missing from my P4A table. S-3 asked for such operations to fail outright; opencode instead asks the user through the `external_directory` permission, so a user can still approve a one-off access. The requirement keeps what every note has in common: nothing outside the active repos is touched silently. |
